# Самостійна робота №9. Делегати й лямбда-вирази: власні утиліти для колекцій

Проєкт: `lab9-self-v19` (варіант 19). Запуск: `dotnet run`.

## Що реалізовано

Статичний клас `CollectionUtils` з чотирма узагальненими методами:

| Метод | Делегат | Призначення | Аналог у LINQ |
|---|---|---|---|
| `Map<TSource, TResult>` | `Func<TSource, TResult>` | перетворює кожен елемент | `Select` |
| `MaxBy<T, TKey>` (`where TKey : IComparable<TKey>`) | `Func<T, TKey>` | знаходить елемент з максимальним ключем | `MaxBy` (.NET 6+) |
| `Filter<T>` | `Predicate<T>` | залишає елементи, що задовольняють умову | `Where` |
| `ForEach<T>` | `Action<T>` | виконує дію для кожного елемента | немає (є `List<T>.ForEach`) |

Рішення, які відрізняються від «мінімального» варіанту з методички:
- `Map` і `Filter` реалізовані через `yield return` (**відкладене виконання**, як і в LINQ), а перевірка аргументів винесена в зовнішній метод, тому `ArgumentNullException` кидається одразу, а не під час перебору.
- `MaxBy` для порожньої колекції кидає `InvalidOperationException` замість того, щоб мовчки повернути `default`, який можна сплутати зі справжнім елементом.
- Усі методи перевіряють аргументи на `null`.

Демонстрація виконана на трьох колекціях: `List<int>`, `List<string>`, `List<Product>`, кожен метод викликається з різними лямбда-виразами.

## Звіт

### Чому делегати корисні для створення таких утиліт?

Метод `Map` або `Filter` містить **алгоритм обходу** (однаковий завжди), а **що саме робити з елементом** різниться від виклику до виклику. Делегат дозволяє передати цю змінну частину як параметр. Без делегатів довелося б писати окремий метод для кожного випадку (`GetNames`, `GetExpensiveProducts`, `GetEvenNumbers`...) або створювати інтерфейси та класи-стратегії. З делегатами один метод покриває нескінченну кількість варіантів, а типи `Func`, `Action`, `Predicate` вже є в бібліотеці, тож власні типи делегатів не потрібні.

### Як лямбда-вирази спрощують виклик цих методів?

Лямбда дає змогу описати поведінку **прямо в місці виклику**, без окремого іменованого методу. Порівняйте:

```csharp
// без лямбди: окремий метод і явне створення делегата
static bool IsExpensive(Product p) => p.Price > 1000;
var expensive = CollectionUtils.Filter(products, IsExpensive);

// з лямбдою: умова видна одразу
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Компілятор сам виводить типи параметрів (`p` це `Product`) і типи узагальнення (`TSource`, `TResult`), тому їх не треба вказувати. Лямбда також може захоплювати локальні змінні (замикання), наприклад `p => p.Price > threshold`.

### Порівняння власних методів із вбудованими LINQ-операторами

| Аспект | Власні методи | LINQ |
|---|---|---|
| Поведінка | `Map` і `Filter` теж працюють відкладено (через `yield`), результат збігається з `Select`/`Where` (перевірено `SequenceEqual` у виводі) | відкладене виконання; багато оптимізацій для масивів і списків (`List<T>`, `Array`) |
| Виклик | статичні методи: `CollectionUtils.Map(list, ...)` | методи розширення: `list.Select(...)`, можна будувати ланцюжки |
| Ланцюжки | вкладені виклики `Filter(Map(...))`, менш читабельно | `list.Where(...).Select(...).OrderBy(...)` |
| `MaxBy` | вимагає `IComparable<TKey>` | приймає ще й власний `IComparer<TKey>`, коректно працює з `null` |
| `ForEach` | є | немає в LINQ навмисно (запити мають бути без побічних ефектів) |
| Повнота | 4 методи | сотні операторів (`GroupBy`, `Join`, `Aggregate`...) |
| Продуктивність | порівнянна для простих випадків | краща завдяки оптимізаціям у .NET |

**Висновок:** власні утиліти корисні для розуміння механізму (делегат + узагальнення + ітератор = LINQ), а в робочому коді варто використовувати LINQ, бо він повніший, оптимізований і знайомий кожному розробнику .NET.

## Відповіді на контрольні запитання

**1. Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?**
Делегат це типізоване посилання на метод. Узагальнений метод залишається незалежним від конкретної логіки, а поведінка приходить ззовні як аргумент. Тип делегата (наприклад, `Func<T, TKey>`) гарантує на етапі компіляції, що передана поведінка має правильну сигнатуру.

**2. У чому різниця між `Func<T, TResult>`, `Action<T>` та `Predicate<T>`?**
`Func<T, TResult>` приймає `T` і **повертає** значення типу `TResult` (перетворення, вибір ключа). `Action<T>` приймає `T` і **нічого не повертає** (`void`), тож використовується для побічних дій (вивід, запис). `Predicate<T>` приймає `T` і повертає `bool`, тобто це спеціалізований `Func<T, bool>` для перевірки умови.

**3. Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?**
Узагальнення дають повторне використання коду для будь-яких типів з безпекою типів, а лямбди роблять передачу поведінки короткою й читабельною. Разом це дозволяє писати декларативний код («які елементи вибрати», а не «як пройти циклом») без дублювання циклів і без приведення типів.

**4. У яких випадках власні утиліти на кшталт `Map` чи `Filter` корисно реалізувати самостійно, навіть якщо існує LINQ?**
Для навчання (щоб зрозуміти, як працюють делегати й ітератори), у середовищах, де LINQ недоступний або небажаний (дуже обмежені платформи, жорсткі вимоги до алокацій), коли потрібна спеціальна семантика (наприклад, інша поведінка для порожньої колекції або `null`, логування, повторні спроби), а також коли треба оптимізований варіант під конкретний тип без проміжних об'єктів.
