# Звіт з аналізу інкапсуляції в Open-Source проєкті

> Самостійна робота №3. Це аналітична робота без власного коду, тож окремого проєкту немає: уся робота у цьому звіті.
> Посилання на рядки наведено для гілки `master` станом на 22.10.2026. Якщо код у репозиторії змінився, шукайте за назвою класу та властивості.

## 1. Обраний проєкт

- **Назва:** Newtonsoft.Json (Json.NET), найпопулярніша бібліотека для роботи з JSON у .NET.
- **Посилання на GitHub:** <https://github.com/JamesNK/Newtonsoft.Json>
- **Чому обрано:** великий зрілий проєкт з багаторічною історією, продуманим публічним API та чіткою структурою (`Src/Newtonsoft.Json/...`). Є класи різного типу: клас налаштувань, клас запису, ієрархія вузлів `JToken` з індексаторами й операторами перетворення.

**Проаналізовані файли:**

| Клас | Файл |
|---|---|
| `JsonSerializerSettings` | [`Src/Newtonsoft.Json/JsonSerializerSettings.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/master/Src/Newtonsoft.Json/JsonSerializerSettings.cs) |
| `JsonWriter` | [`Src/Newtonsoft.Json/JsonWriter.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/master/Src/Newtonsoft.Json/JsonWriter.cs) |

## 2. Аналіз інкапсуляції

### Клас: `JsonSerializerSettings`

- **Опис класу:** контейнер налаштувань серіалізації: формат дат, глибина вкладеності, обробка null, список конвертерів, резолвер контрактів тощо. Користувач створює об'єкт, змінює потрібні властивості й передає його серіалізатору.
- **Поля:** кожне налаштування зберігається у «службовому» полі з префіксом `_`, але в цьому класі вони оголошені як `internal`, а не `private` (рядки 72-95). Це означає, що вони приховані від користувачів бібліотеки, але доступні іншим класам тієї ж збірки (серіалізатор читає їх напряму). Публічними є лише властивості. Поля мають тип `Nullable` (`int?`, `Formatting?`), щоб розрізняти «значення не задано» і «задано»:

```csharp
internal const int DefaultMaxDepth = 64;      // рядок 70: значення за замовчуванням
internal int? _maxDepth;                       // рядок 81: що задав користувач
internal bool _maxDepthSet;                    // рядок 82: чи задавав
```

- **Властивості:** є і прості автоматичні, і властивості з логікою.
  - Автоматичні `get; set;` для налаштувань без обмежень:

```csharp
public IList<JsonConverter> Converters { get; set; }          // рядок 156
public IContractResolver? ContractResolver { get; set; }       // рядок 235
public IEqualityComparer? EqualityComparer { get; set; }       // рядок 241
```

  - Ініціалізація колекції робиться в конструкторі (`Converters = new List<JsonConverter>();`, рядок 459), щоб користувач ніколи не отримав `null`.
  - Властивості з логікою (див. нижче `MaxDepth`): повертають значення за замовчуванням, поки користувач нічого не задав.
  - Властивостей лише для читання чи лише для запису в цьому класі немає: це клас налаштувань, усе має бути змінним.
- **Індексатори/оператори:** немає.

### Клас: `JsonWriter`

- **Опис класу:** абстрактний базовий клас для запису JSON (послідовний, «потоковий» запис). Тримає внутрішній стан автомата (чи можна зараз писати значення, ключ чи закрити об'єкт).
- **Поля:** **приватні** і ховають внутрішній стан, який не можна змінювати ззовні, бо інакше запис порушить синтаксис JSON (рядки 119-122):

```csharp
private List<JsonPosition>? _stack;
private JsonPosition _currentPosition;
private State _currentState;
private Formatting _formatting;
```

- **Властивості:** автоматичні для простих налаштувань:

```csharp
public bool CloseOutput { get; set; }          // рядок 130
public bool AutoCompleteOnClose { get; set; }  // рядок 138
```

  Їхні значення за замовчуванням (`true`) виставляються в конструкторі (рядки 352-353). Властивість `Formatting` має власне поле `_formatting` і перевірку значення (див. розділ 3).
- **Індексатори/оператори:** немає.

### Клас: `JToken` (та похідні `JObject`, `JArray`)

- **Опис класу:** базовий клас для будь-якого вузла JSON-дерева (об'єкт, масив, значення). Дозволяє читати й змінювати JSON як структуру в пам'яті.
- **Поля:** зв'язок із батьківським вузлом зберігається в приватному полі (рядок 65):

```csharp
private JContainer? _parent;
```

- **Властивості:** показовий приклад **асиметричного доступу**: читати батька може будь-хто, а змінювати лише сама бібліотека (рядки 134-139):

```csharp
public JContainer? Parent
{
    [DebuggerStepThrough]
    get { return _parent; }
    internal set { _parent = value; }   // зовнішній код змінити не може
}
```

  Тобто властивість публічно «лише для читання», а `internal set` дозволяє збірці підтримувати цілісність дерева (вузол не може мати двох батьків).
- **Індексатори:** `JToken` оголошує віртуальний індексатор за ключем, який у базовому класі **навмисно кидає виняток**, бо не всі вузли мають дітей (рядки 356-360):

```csharp
public virtual JToken? this[object key]
{
    get => throw new InvalidOperationException("Cannot access child value on {0}.".FormatWith(CultureInfo.InvariantCulture, GetType()));
    set => throw new InvalidOperationException("Cannot set child value on {0}.".FormatWith(CultureInfo.InvariantCulture, GetType()));
}
```

  Похідні класи перевизначають його: у `JObject` ключем є ім'я властивості (`this[string propertyName]`, `override this[object key]`, рядки 331 і 361 файлу `JObject.cs`), у `JArray` це числовий індекс (`this[int index]`, рядок 288 файлу `JArray.cs`). Тож `obj["name"]` та `array[0]` виглядають однаково, але працюють по-різному (поліморфізм + інкапсуляція внутрішньої структури).
- **Оператори:** `JToken` визначає **35 неявних** (`implicit`) та **37 явних** (`explicit`) операторів перетворення. Неявні дозволяють просто написати `JToken t = "text";` чи `token = 42;`:

```csharp
public static implicit operator JToken(string? value)   // рядок 1854
{
    return new JValue(value);
}
```

  Явні перетворення в зворотному напрямку (`(int)token`, рядок 819) вимагають явного приведення, бо вони можуть завершитись помилкою (вузол може містити не число). Правило виконане: **неявно тільки безпечні перетворення, явно небезпечні**.

## 3. Практики валідації у властивостях

### Приклад 1: перевірка діапазону значення і `ArgumentOutOfRangeException` (`JsonWriter.Formatting`, рядки 235-246)

```csharp
public Formatting Formatting
{
    get => _formatting;
    set
    {
        if (value < Formatting.None || value > Formatting.Indented)
        {
            throw new ArgumentOutOfRangeException(nameof(value));
        }

        _formatting = value;
    }
}
```

Сценарій: `Formatting` це перелік (`enum`), у який через приведення типів можна «запхати» будь-яке число (`(Formatting)99`). Сеттер перевіряє, що значення належить до дозволених, і лише потім записує його в приватне поле. Така сама перевірка повторюється й для інших налаштувань (рядки 242, 259, 276, 293, 318).

### Приклад 2: перевірка «значення має бути додатним» і `ArgumentException` (`JsonSerializerSettings.MaxDepth`, рядки 337-349)

```csharp
public int? MaxDepth
{
    get => _maxDepthSet ? _maxDepth : DefaultMaxDepth;
    set
    {
        if (value <= 0)
        {
            throw new ArgumentException("Value must be positive.", nameof(value));
        }

        _maxDepth = value;
        _maxDepthSet = true;
    }
}
```

Сценарій: максимальна глибина вкладеності JSON не може бути нулем або від'ємною (`null` дозволений і означає «без обмеження»). Сеттер відхиляє некоректні значення одразу, з зрозумілим повідомленням і назвою параметра (`nameof(value)`). Геттер реалізує «ліниве» значення за замовчуванням: поки користувач не задав глибину, повертається 64.

### Приклад 3: перевірка на `null` і типу ключа в індексаторі (`JObject`, рядки 331-342)

```csharp
public override JToken? this[object key]
{
    get
    {
        ValidationUtils.ArgumentNotNull(key, nameof(key));

        if (!(key is string propertyName))
        {
            throw new ArgumentException("Accessed JObject values with invalid key value: {0}. Object property name expected.".FormatWith(...));
        }

        return this[propertyName];
```

Сценарій: індексатор отримує `object`, а `JObject` приймає тільки рядкові ключі. Спочатку допоміжний клас `ValidationUtils` перевіряє, що ключ не `null`, потім перевіряється тип; помилка пояснює, що саме очікувалось.

### Приклад 4: валідація через обмеження доступу (`JToken.Parent`, `internal set`)

Це «валідація без `if`»: замість того щоб перевіряти, чи користувач не присвоїв `Parent` некоректне значення, бібліотека просто не дає змінювати його ззовні (рядок 138). Цілісність дерева гарантується модифікатором доступу.

### Атрибути валідації `DataAnnotations`

У проаналізованих класах атрибути з `System.ComponentModel.DataAnnotations` **не використовуються**: бібліотека валідує свій стан явними перевірками й винятками. Єдина згадка `DataAnnotations` у файлі `JsonTypeReflector.cs` (рядок 332) стосується підтримки `MetadataTypeAttribute`, тобто читання метаданих користувацьких класів, а не валідації власних.

### Висновки щодо валідації

- **Використані підходи:** (1) явні `if` у `set` з винятками `ArgumentOutOfRangeException` та `ArgumentException`; (2) допоміжні статичні методи (`ValidationUtils.ArgumentNotNull`) для повторюваних перевірок; (3) обмеження доступу (`internal set`, приватні поля); (4) Nullable-типи й прапорці (`_maxDepthSet`) для розрізнення «не задано» і «задано»; (5) значення за замовчуванням у конструкторі.
- **Переваги:** некоректний стан не може потрапити в об'єкт, помилка виникає **там, де її зроблено** (у сеттері), а не десь далеко під час серіалізації; повідомлення зрозумілі, а `nameof(value)` вказує параметр. Валідація в одному місці (сеттері) діє для всіх сценаріїв використання.
- **Недоліки:** код валідації вручну повторюється в кількох властивостях; винятки в сеттерах не підходять для масової валідації форм (там краще збирати всі помилки, а не падати на першій); атрибути (`DataAnnotations`) були б декларативнішими, але вони не перевіряються автоматично без додаткового коду (потрібен валідатор).

## 4. Загальні висновки

Проєкт демонструє зрілу інкапсуляцію: **стан прихований** (приватні й `internal` поля), **доступ контрольований** (властивості з `get/set`, асиметричні рівні доступу `get` публічний / `set` внутрішній), **коректність гарантується на межі класу** (валідація в сеттерах і індексаторах), а **API природний для користувача** (індексатори `obj["key"]`, неявні перетворення `JToken t = "text"`). Водночас автори не доводять інкапсуляцію до абсурду: прості налаштування (`CloseOutput`, `Converters`) це звичайні автоматичні властивості, а складна логіка з'являється лише там, де є що захищати. Поля `JsonSerializerSettings` мають рівень `internal`, а не `private`: це компроміс між суворою інкапсуляцією та продуктивністю й зручністю доступу всередині збірки.

## Відповіді на контрольні запитання

**1. За якими ознаками можна зробити висновок, що в класі дотримано інкапсуляції?**
Поля приховані (`private`/`internal`), а доступ до даних іде через властивості та методи; зміна стану контролюється (валідація в `set`, асиметричні рівні доступу, як у `JToken.Parent`); внутрішня структура може змінитись без зміни публічного API; об'єкт не можна привести в некоректний стан зовнішнім кодом; колекції не віддаються так, щоб їх можна було зіпсувати.

**2. Які підходи до валідації властивостей ви зустріли в реальному коді?**
Перевірки `if` у сеттері з винятками `ArgumentOutOfRangeException` та `ArgumentException` (`Formatting`, `MaxDepth`); допоміжні методи перевірок (`ValidationUtils.ArgumentNotNull`); перевірка типу аргументу в індексаторі (`JObject`); обмеження доступу замість перевірки (`internal set` у `Parent`); використання `Nullable` та окремих прапорців для значень за замовчуванням. Атрибути `DataAnnotations` у проаналізованих класах не застосовуються.

**3. Чому для аналізу важливо наводити посилання на конкретні класи та фрагменти коду?**
Щоб висновки можна було **перевірити**: читач відкриває файл і бачить те саме; без посилань аналіз стає загальними словами. Конкретні фрагменти доводять, що автор справді вивчив код, а не переказав теорію, і дозволяють порівнювати різні підходи на реальних прикладах. Також проєкти змінюються: посилання на файл, рядки й дата фіксують, який саме стан коду аналізувався.

**4. Які висновки щодо якості проєктування ви зробили?**
Проєкт добре спроєктований: інтерфейс користувача простий і природний (індексатори, неявні перетворення), складність прихована всередині, помилки виявляються рано завдяки валідації в сеттерах, а цілісність структури (дерево `JToken`) захищена модифікаторами доступу. Недоліки незначні: деяка повторюваність коду перевірок і використання `internal` полів замість `private` у класі налаштувань (компроміс на користь простоти внутрішнього доступу).
