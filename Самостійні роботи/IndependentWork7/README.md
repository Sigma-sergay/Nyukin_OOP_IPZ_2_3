# Самостійна робота №7. Узагальнений кеш `Cache<TKey, TValue>` із тестами

## Структура

```
IndependentWork7/          # основний проєкт
├── Cache.cs               # Cache<TKey, TValue> (FIFO)
└── Program.cs             # демонстрація в консолі
IndependentWork7.Tests/    # xUnit-тести (посилається на IndependentWork7)
└── CacheTests.cs          # 19 тестів
```

Запуск: `dotnet run --project IndependentWork7`, тести: `dotnet test IndependentWork7.Tests`.

## Реалізація

- `_capacity` (`int`) - максимальна кількість елементів.
- `_cache` (`Dictionary<TKey, TValue>`) - зберігає пари ключ-значення, пошук за ключем в середньому за O(1).
- `_keysOrder` (`Queue<TKey>`) - порядок додавання ключів. Найстаріший ключ завжди на початку черги.
- `Add`: якщо ключ уже є, значення оновлюється (позиція в черзі не змінюється). Інакше, якщо кеш повний, робиться `Dequeue()` і цей ключ видаляється зі словника, після чого новий елемент додається у словник і в кінець черги.
- `Get`: використовує `TryGetValue`, а не індексатор, і сам кидає `KeyNotFoundException` з зрозумілим повідомленням.
- `ContainsKey` та `Count` лише читають стан.
- Конструктор з ємністю `<= 0` кидає `ArgumentOutOfRangeException`.
- Обмеження `where TKey : notnull` узгоджене з вимогою `Dictionary` (ключ не може бути `null`).

LRU-розширення (необов'язкове) не реалізовувалось: за завданням основне рішення це FIFO.

## Тести (19)

| Група | Що перевіряється |
|---|---|
| Конструктор | нульова та від'ємна ємність → виняток |
| Add | додавання одного й кількох елементів, оновлення наявного ключа без зміни `Count` |
| Get | існуючий ключ, відсутній ключ → `KeyNotFoundException`, порожній кеш |
| ContainsKey | є / немає |
| Count | порожній кеш = 0, `Count` ніколи не перевищує ємність |
| FIFO | витісняється найстаріший, інші й новий лишаються, порядок витіснення при багатьох вставках, `Get` не «омолоджує» елемент (це не LRU), оновлення ключа не витісняє нічого й не змінює його позицію, ємність 1 |

## Приклад виводу програми

```
Створено кеш ємністю 3 (політика FIFO)
Додано a, b, c. Count = 3
Get("a") = Альфа

Додаємо ключ d: кеш повний, найстаріший (a) має зникнути
Count = 3
  ContainsKey("a") = False
  ContainsKey("b") = True
  ContainsKey("c") = True
  ContainsKey("d") = True

Додаємо ключ e: тепер має зникнути b
  ContainsKey("b") = False
  ContainsKey("c") = True
  ContainsKey("d") = True
  ContainsKey("e") = True

Спроба отримати видалений ключ:
  KeyNotFoundException: Ключ 'a' не знайдено в кеші.
```

## Відповіді на контрольні запитання

**1. Які переваги надає `Cache<TKey, TValue>` порівняно з окремими неузагальненими реалізаціями кешу?**
Один клас замість окремих `StringCache`, `IntCache`, `ProductCache`. Компілятор перевіряє типи, тому в кеш `Cache<int, string>` не можна покласти значення іншого типу. Не потрібні приведення типів, а для значущих типів немає упаковки (boxing), на відміну від кешу на `object`. Код і тести пишуться один раз для всіх типів.

**2. Чому для реалізації політики FIFO зручно поєднувати `Dictionary<TKey, TValue>` з `Queue<TKey>` або `LinkedList<TKey>`?**
Кожна структура робить те, що вміє найкраще: `Dictionary` дає пошук за ключем за O(1), але не пам'ятає порядок додавання; `Queue` зберігає порядок і дає видалення найстаршого за O(1) (`Dequeue`), але не вміє швидко шукати за ключем. Разом вони забезпечують і швидкий `Get`, і швидке витіснення. `LinkedList<TKey>` потрібен для LRU, бо дозволяє за O(1) переносити довільний вузол у кінець списку при кожному зверненні, чого `Queue` не вміє.

**3. У яких випадках метод `Get` повинен викидати `KeyNotFoundException`, а коли доцільніше використовувати підхід на кшталт `TryGetValue`?**
Виняток підходить, коли відсутність ключа це помилка в логіці програми (ключ мав би бути там), і викликач не очікує промаху. Для кешу, де відсутність ключа це **нормальна, часта ситуація** (cache miss), краще шаблон `TryGet(key, out value)`: він не створює дорогий виняток і дозволяє написати `if (!cache.TryGet(...)) { обчислити й додати }`. У цій роботі за вимогою завдання `Get` кидає виняток, а `ContainsKey` дозволяє перевірити наявність заздалегідь.

**4. Які тести є критично важливими для перевірки політики витіснення елементів з кешу?**
(а) Видаляється саме найстаріший елемент, а не будь-який; (б) решта елементів і новий елемент лишаються; (в) `Count` не перевищує ємність; (г) порядок витіснення зберігається при багатьох вставках поспіль; (д) читання (`Get`) не змінює порядок (відрізняє FIFO від LRU); (е) оновлення наявного ключа не викликає зайвого витіснення; (є) граничний випадок ємності 1.
