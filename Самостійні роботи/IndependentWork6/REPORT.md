# Самостійна робота №6. Інтерфейс vs абстрактний клас

Проєкт: `IndependentWork6`. Запуск: `dotnet run`.
Спершу я зіставив характеристики кожного сценарію з критеріями вибору (розділ «Загальні висновки»), і лише потім написав код.

## Сценарій 1: Система сповіщень

### Обраний підхід: інтерфейс `INotifier`

### Обґрунтування вибору

1. **Канали не мають спільного стану й спільної реалізації.** Email потребує адреси, SMS номера й обмеження довжини, Push токена пристрою. Єдине спільне це контракт `Send(string message)`. Абстрактному класові нічого було б «винести нагору», окрім порожнього методу.
2. **Множинна поведінка.** C# не має множинного наслідування класів, але клас може реалізувати кілька інтерфейсів. `EmailNotifier` реалізує і `INotifier`, і `ILoggable`. Якби `INotifier` був абстрактним класом, будь-який клас, який уже наслідує інший базовий клас (наприклад, від бібліотечного), не зміг би стати сповіщувачем.
3. **Слабке зв'язування й тестованість.** Клієнтський код працює з `INotifier` і не знає, як саме відправляється повідомлення. У тестах легко підставити заглушку.
4. **Додавання нових каналів** (Telegram, Viber) не вимагає ні базового класу, ні змін наявного коду: достатньо реалізувати інтерфейс.

### Чому абстрактний клас тут менш доречний

Абстрактний клас `NotifierBase` змусив би всі канали бути нащадками одного предка заради єдиного методу. Він створює жорстке зв'язування, блокує успадкування від іншого класу й додає «базовий код», який нічого не робить. Якби з'явилась реальна спільна логіка (наприклад, повторні спроби відправки), її можна було б винести окремо (композиція або допоміжний клас), не змінюючи контракт.

### Реалізація

```csharp
public interface INotifier
{
    void Send(string message);
}

public class SmsNotifier : INotifier
{
    private readonly string _phone;
    public SmsNotifier(string phone) { _phone = phone; }

    public void Send(string message)
    {
        string text = message.Length > 40 ? message[..37] + "..." : message;
        Console.WriteLine($"[SMS -> {_phone}] {text}");
    }
}

// Демонстрація в Main
List<INotifier> notifiers = new()
{
    new EmailNotifier("olena@example.com"),
    new SmsNotifier("+380501234567"),
    new PushNotifier("a1b2c3")
};
foreach (INotifier notifier in notifiers)
    notifier.Send("Ваше замовлення №1024 відправлено та буде доставлене завтра.");
```

## Сценарій 2: Обробка файлів

### Обраний підхід: абстрактний клас `FileProcessor`

### Обґрунтування вибору

1. **Спільні кроки.** Відкриття і закриття файлу однакові для всіх типів. Їх варто написати один раз у базовому класі, а не дублювати в кожному обробнику. Абстрактний клас може містити готову реалізацію (`Open`, `Close`), інтерфейс (у класичному вигляді) ні.
2. **Шаблонний метод.** Порядок кроків зафіксований у `Process()`: відкрити → обробити → закрити (у `finally`). Нащадки заповнюють лише `ProcessContent()`. Тому неможливо «забути закрити файл»: гарантію дає базовий клас.
3. **Спільний стан.** Поле `_reader` і властивість `FilePath` належать усім обробникам. Інтерфейс не може містити поля екземпляра.
4. **Контроль доступу.** Кроки `Open`/`Close` приватні, `ProcessContent` захищений (`protected abstract`): нащадок бачить рівно те, що йому потрібно.
5. **Справжнє відношення «є різновидом».** `TextFileProcessor`, `XmlFileProcessor`, `CsvFileProcessor` є різновидами обробника файлу, тож наслідування природне.

### Чому інтерфейс тут менш доречний

З `IFileProcessor` довелося б у кожному класі (`Text`, `Xml`, `Csv`) повторювати відкриття, закриття, `try/finally`. Дублювання означає ризик помилок: достатньо в одному обробнику забути `finally`, і файл лишиться відкритим. (У C# 8+ інтерфейси можуть мати реалізацію за замовчуванням, але вони досі не можуть зберігати стан екземпляра, тому для цього сценарію це не підходить.)

### Реалізація

```csharp
public abstract class FileProcessor
{
    private StreamReader? _reader;
    public string FilePath { get; }
    protected FileProcessor(string filePath) { FilePath = filePath; }

    protected StreamReader Reader =>
        _reader ?? throw new InvalidOperationException("Файл не відкрито.");

    public void Process()            // шаблонний метод
    {
        Open();
        try { ProcessContent(); }
        finally { Close(); }
    }

    private void Open()  { _reader = new StreamReader(FilePath); }
    private void Close() { _reader?.Dispose(); _reader = null; }

    protected abstract void ProcessContent();   // унікальна логіка
}

public class XmlFileProcessor : FileProcessor
{
    public XmlFileProcessor(string filePath) : base(filePath) { }

    protected override void ProcessContent()
    {
        XDocument doc = XDocument.Load(Reader);
        Console.WriteLine($"  XML-файл: усього елементів - {doc.Descendants().Count()}");
    }
}
```

Обидва сценарії демонструють поліморфізм: `List<INotifier>` і `List<FileProcessor>` містять різні реалізації, а цикл викликає однаковий метод (`Send`, `Process`).

## Загальні висновки: практичні критерії вибору

| Питання | Якщо «так» → | Приклад |
|---|---|---|
| Реалізації мають **спільний код або стан**, який варто не дублювати? | абстрактний клас | `FileProcessor` (відкриття/закриття, `_reader`) |
| Реалізації **не пов'язані між собою**, їх об'єднує лише вміння щось робити? | інтерфейс | `INotifier` (Email, SMS, Push) |
| Клас має поєднувати **кілька ролей** (сповіщувач + логер)? | інтерфейс | `EmailNotifier : INotifier, ILoggable` |
| Потрібен **фіксований порядок кроків** (шаблонний метод)? | абстрактний клас | `Process()` |
| Потрібно, щоб **будь-який** клас міг підключитись до системи, навіть з іншим предком? | інтерфейс | сторонні типи |
| Потрібні **захищені члени, поля, конструктор**? | абстрактний клас | `protected Reader` |
| Контракт має бути **максимально стабільним і мінімальним**? | інтерфейс | один метод `Send` |

Практичне правило: **інтерфейс описує «що вміє» (can-do), абстрактний клас описує «чим є» (is-a) і дає частину готової реалізації**. Їх можна комбінувати: абстрактний клас, що реалізує інтерфейс (поширений патерн у бібліотеках .NET). Обидва підходи підтримують принцип інверсії залежностей (DIP): код залежить від абстракції, а не від конкретного класу.

## Відповіді на контрольні запитання

**1. Які ознаки підказують, що сценарій краще моделювати через інтерфейс?**
Реалізації не пов'язані спільним предком і не мають спільного коду чи стану; важливий лише контракт; класу може знадобитися кілька ролей одночасно; хочеться максимального слабкого зв'язування й простоти тестування (заміна заглушкою). У сценарії зі сповіщеннями так і було.

**2. У чому перевага абстрактного класу для процесів зі спільними кроками виконання?**
Він дозволяє написати спільні кроки один раз і зафіксувати їхній порядок (шаблонний метод), залишивши нащадкам лише унікальну частину. Це прибирає дублювання, гарантує коректне закриття ресурсів (`finally` в одному місці) і зберігає спільний стан. В інтерфейсі такого стану немає.

**3. Як порівняння двох підходів допомагає прийняти архітектурне рішення?**
Порівняння змушує назвати конкретні критерії (спільний код, стан, кілька ролей, фіксований алгоритм) і перевірити їх щодо сценарію, замість того щоб вибирати «за звичкою». Також видно ціну альтернативи: дублювання коду для інтерфейсу в сценарії з файлами або зайве жорстке зв'язування для абстрактного класу в сценарії зі сповіщеннями. Рішення стає аргументованим і його можна відстояти.

**4. Яку роль у ваших прикладах відіграє поліморфізм?**
В обох сценаріях колекція містить посилання на базовий тип (`INotifier` або `FileProcessor`), а під час виклику виконується метод реального типу об'єкта. Цикл не знає, чи це Email чи SMS, XML чи CSV. Завдяки цьому нові канали й нові типи файлів додаються без змін у коді, який ними користується.
