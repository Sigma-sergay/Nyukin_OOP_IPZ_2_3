# Самостійна робота №20 — Реалізація exponential backoff

**Виконав:** Нюкін Сергій, ІПЗ-3/2
**Проєкт:** `IndependentWork14` (.NET 10, без сторонніх пакетів)

```
dotnet run --project IndependentWork14
```

## Обрані параметри

| Параметр | Значення | Чому |
|----------|----------|------|
| `maxRetries` | 4 | сервер складу після перезапуску зазвичай піднімається за 1–2 с; 4 повтори покривають ≈ 2,25 с |
| `initialDelay` | 150 мс | достатньо мало, щоб короткий збій не було помітно користувачу |
| `jitterFactor` | 0.2 | ±20 % розводить у часі повтори багатьох клієнтів, але не робить паузи непередбачувано довгими |

**Сценарій:** резервування товарів кошика на сервері складу, який після перезапуску відповідає `503 Service Unavailable`.

## Клас `RetryPolicy`

- Приватні поля: `_maxRetries`, `_initialDelay`, `_jitterFactor` (і `_random`).
- Конструктор `RetryPolicy(int maxRetries, TimeSpan initialDelay, double jitterFactor = 0.2)` перевіряє аргументи.
- Узагальнений метод `T Execute<T>(Func<T> operation, Func<Exception, bool>? shouldRetry = null)`.
- Затримка рахується **за формулою з методички**:

```csharp
double jitter = 1 + _random.NextDouble() * _jitterFactor * 2 - _jitterFactor;   // від 0.8 до 1.2
double ms = _initialDelay.TotalMilliseconds * Math.Pow(2, retryAttempt) * jitter;
```

- Кожна спроба, затримка (фактична й базова) і причина невдачі логуються через `Console.WriteLine`.
- Якщо `shouldRetry` повертає `false` або спроби вичерпано, виняток передається далі через `throw;` зі збереженням стека.

## Демонстрація в `Main`

| Сценарій | Що відбувається | Результат |
|----------|-----------------|-----------|
| 1. Успіх після кількох спроб | склад відповідає 503 тричі | успіх на 4-й спробі; затримки 146 / 312 / 566 мс (бази 150 / 300 / 600) |
| 2. Остаточна невдача | склад недоступний постійно | 5 викликів, затримки 142 / 344 / 700 / 1427 мс, потім `HttpRequestException` у `Main` |
| 3. `shouldRetry = false` | некоректна кількість товарів (−5) | `ArgumentOutOfRangeException` одразу, 1 виклик, без повторів |
| 4. Інший тип `T` | `Execute<string>` для отримання токена | успіх на 2-й спробі, показує узагальненість класу |

Фрагмент виводу (сценарій 2):

```
Спроба 4/5
✗ HttpRequestException: 503 Service Unavailable: склад перезапускається (кошик #2077).
Затримка перед повтором: 1427 мс (база 1200 мс)
Спроба 5/5
✗ HttpRequestException: 503 Service Unavailable: склад перезапускається (кошик #2077).
Вичерпано 4 повторних спроб → виняток передається далі
Main перехопив виняток після 5 викликів: 503 Service Unavailable: склад перезапускається (кошик #2077).
```

Видно, що фактична затримка відрізняється від бази в межах ±20 %: це і є jitter.

## Висновок щодо меж застосування Retry з exponential backoff

Retry з експоненційною затримкою та jitter ефективний для **тимчасових** збоїв: перезапуск сервісу, `503`/`429`, мережевий таймаут. Паузи, що зростають, дають залежності час відновитися, а jitter не дає всім клієнтам повторювати запити синхронно. Водночас патерн **не допомагає** при постійних помилках (некоректні дані, немає прав), бо лише збільшує час до неминучої відмови. Тому `shouldRetry` має пропускати тільки перехідні помилки. Загальний час очікування зростає експоненційно, тож `maxRetries` треба обмежувати з огляду на допустиму затримку для користувача. Повтор небезпечний для неідемпотентних операцій (оплата, створення замовлення) без ключа ідемпотентності. Якщо залежність лежить довго, краще поєднати Retry з Circuit Breaker.

## Відповіді на контрольні запитання

**1. Чому експоненційна затримка ефективніша за фіксовану для тимчасових збоїв?** Фіксована пауза або занадто коротка (сервіс ще не відновився, а його знову навантажують), або занадто довга (короткий збій змушує довго чекати). Експоненційна починає з малої паузи, тож короткий збій долається швидко, а якщо збій затягується, паузи ростуть (150 → 300 → 600 → 1200 мс). Навантаження на сервіс, що відновлюється, зменшується, і загальна кількість спроб лишається невеликою.

**2. Для чого потрібен jitter і як він зменшує ризик одночасних повторних спроб?** Якщо сотні клієнтів отримали помилку в ту саму мить, з однаковою формулою затримки вони й повторять запит у ту саму мить: виникає хвиля (thundering herd), яка знову перевантажує сервіс. Jitter додає випадкове відхилення (тут ±20 %), і повтори різних клієнтів розподіляються в часі.

**3. Яку роль відіграє `shouldRetry`?** Делегат відділяє тимчасові помилки, які варто повторювати (`HttpRequestException`, `TimeoutException`), від постійних (`ArgumentOutOfRangeException`, `UnauthorizedAccessException`), для яких повтор марний. Завдяки цьому `RetryPolicy` лишається узагальненим, а рішення «що повторювати» приймає код, який знає конкретну операцію (сценарій 3).

**4. У яких випадках повторна спроба не є безпечною?** Для **неідемпотентних** операцій, коли повтор може виконати дію двічі: списання коштів, створення замовлення, надсилання листа чи SMS, збільшення лічильника. Якщо відповідь загубилась після фактичного виконання, повтор дублює дію. Такі операції не повторюють автоматично або захищають ключем ідемпотентності. Також не варто повторювати при помилках авторизації (можна заблокувати акаунт) і при перевантаженні, про яке сервер явно повідомив (`429` без `Retry-After`).
