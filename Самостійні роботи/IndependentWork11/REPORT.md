# Самостійна робота №11. LINQ pipelines: ETL та аналітика

Проєкт: `IndependentWork11`, сценарій «Продажі». Запуск: `dotnet run` (для коректних вимірювань: `dotnet run -c Release`).

## 1. Модель і дані

- `Sale` (Id, ProductId, Quantity, SaleDate, CustomerId), `Product` (Id, Name, Category, UnitPrice), `Customer` (Id, Name, City).
- Дані генеруються `DataGenerator` з фіксованим `Random(42)`, тому результати відтворювані: **100 продуктів** у 8 категоріях, **80 клієнтів** у 10 містах, **1000 продажів** з 01.01.2024 до 01.10.2026.
- Кожен пайплайн оформлено окремим методом класу `Pipelines`, тож `Main` лишається коротким: створити дані, викликати метод, вивести результат і час.

## 2. Пайплайни

### Пайплайн 1: `TopProductsByCategory` (найпопулярніші продукти за категоріями)
**Мета:** для кожної категорії знайти 3 продукти з найбільшою кількістю проданих одиниць.
**Оператори:** `GroupBy` (продажі за продуктами) → `Select` з `Sum` (кількість на продукт) → `Join` з продуктами (назва, категорія) → `GroupBy` (за категорією) → `OrderByDescending` + `Take(3)` (топ-3) → `OrderBy` (стабільний порядок категорій).
**Чому так:** `Sale` не містить назви й категорії, тому потрібне з'єднання (`Join`); спочатку агрегуємо продажі (набагато менше записів), і лише потім з'єднуємо: так `Join` працює з 100 записами, а не з 1000.

### Пайплайн 2: `RevenueByCity` (дохід за містами клієнтів)
**Мета:** загальний дохід по кожному місту, від найбільшого.
**Оператори:** `Join` з продуктами (ціна) → `Join` з клієнтами (місто) → `Select` (`Quantity * UnitPrice`) → `GroupBy` (місто) → `Sum` → `OrderByDescending`.
**Чому так:** дані про ціну, місто й кількість живуть у трьох різних колекціях (нормалізована модель, як у реляційній БД), тому для аналітики їх треба з'єднати.

### Пайплайн 3: `SalesByMonth` (продажі за роками й місяцями)
**Мета:** кількість проданих одиниць і дохід по кожному місяцю.
**Оператори:** `Join` з продуктами → `GroupBy` за **складеним ключем** `new { Year, Month }` → `Sum` (кількість і дохід) → `OrderBy(Year)` + `ThenBy(Month)`.
**Чому так:** складений ключ (анонімний тип) групує по двох полях одразу, а `OrderBy/ThenBy` дає хронологічний порядок.

### Пайплайн 4 (власний): `TopCustomersWithFavoriteCategory`
**Мета:** топ-5 клієнтів за витратами та їхня улюблена категорія (де вони купили найбільше одиниць).
**Оператори:** `Join` з продуктами → `GroupBy` (клієнт) → `Select` з вкладеним `GroupBy` + `OrderByDescending` + `ThenBy` + `First` (улюблена категорія) → `Join` з клієнтами (ім'я, місто) → `OrderByDescending` + `Take(5)`.
**Чому так:** це типова бізнес-аналітика (сегментація клієнтів). Вкладений `GroupBy` усередині `Select` обчислює показник для кожної групи окремо; `ThenBy(cg => cg.Key)` робить вибір детермінованим при рівності.

## 3. Вивід програми та вимірювання часу

Для кожного пайплайну створюється **новий** `Stopwatch`. Міряються два значення: **перший запуск** (включає JIT-компіляцію й початкове «розігрівання») та **середнє за 200 повторів** після прогріву. Результати матеріалізуються через `ToList()`, щоб міряти справжнє виконання, а не лише побудову відкладеного запиту.

## 4. Аналіз продуктивності

| Пайплайн | Перший запуск, мс | Після прогріву (середнє), мс |
|---|---|---|
| 1. Топ продуктів за категоріями | 16.77 | 0.323 |
| 2. Дохід за містами | 5.19 | 0.494 |
| 3. Продажі за місяцями | 3.52 | 0.413 |
| 4. Топ клієнтів і улюблена категорія | 4.91 | 0.851 |

(Режим Release, контейнер з 1 ядром; на вашому комп'ютері числа відрізнятимуться, але співвідношення мають зберегтися.)

**Які фактори вплинули на час виконання:**
1. **JIT-компіляція та прогрів.** Перший запуск у 6-50 разів повільніший за наступні, бо виконується компіляція методів LINQ та створення узагальнених типів. Саме тому одне вимірювання `Stopwatch` без прогріву вводить в оману.
2. **Кількість і вид операцій.** Найдорожчим є пайплайн 4: він має два `Join`, `GroupBy` та вкладений `GroupBy` для кожного клієнта (операція над групою всередині групи). Пайплайн 1 найшвидший, бо агрегує до `Join` і з'єднує лише 100 записів.
3. **Розмір даних.** Для 1000 продажів усе відбувається за частки мілісекунди; на мільйонах записів різниця між пайплайнами зростає (вартість `Join` і `GroupBy` близька до лінійної: LINQ будує хеш-таблицю для з'єднання).
4. **Порядок операцій.** Агрегування до з'єднання (пайплайн 1) зменшує обсяг даних для наступних кроків.
5. **Виділення пам'яті та збирач сміття.** Проміжні групи й анонімні об'єкти створюють навантаження на GC; воно додає шум до вимірювань.
6. **Матеріалізація.** `ToList()` змушує виконати запит повністю; без нього час вимірював би лише створення відкладеного запиту.

## 5. Висновки щодо ефективності LINQ для ETL та аналітики

- LINQ дає **декларативний** опис («що отримати»), а не «як це зробити циклами»: пайплайни по 8-15 рядків замість десятків рядків вкладених циклів з проміжними словниками.
- **Join/GroupBy/OrderBy/Sum** покривають типові ETL-кроки (Extract: джерело; Transform: проєкція, з'єднання, агрегація; Load: `ToList()`).
- Продуктивність достатня для даних, що поміщаються в пам'ять (тисячі-мільйони записів); для великих обсягів або баз даних краще перекладати запит на SQL (LINQ to Entities) або використовувати спеціалізовані засоби.
- Ціна зручності: проміжні об'єкти й відкладене виконання (запит може виконатися кілька разів або не там, де очікується, якщо не матеріалізувати результат).
- Для великих запитів варто розбивати пайплайн на іменовані кроки, тоді код лишається читабельним.

## Відповіді на контрольні запитання

**1. Які переваги дає LINQ для побудови ETL-пайплайнів порівняно з ручними циклами?**
Декларативність і стислість (видно намір, а не механіку), композиція (оператори з'єднуються в ланцюжок), менше проміжних змінних і помилок індексів, єдина мова запитів для різних джерел (колекції, XML, БД), легка зміна порядку кроків і можливість відкладеного виконання.

**2. Чому для аналітичних задач часто поєднують `Join`, `GroupBy`, `Select` та `OrderBy` в одному пайплайні?**
Аналітика зазвичай складається з чотирьох кроків: зібрати дані з різних таблиць (`Join`), згрупувати за вимірами (`GroupBy`), обчислити показники (`Select` із `Sum/Count/Average`) і впорядкувати результат (`OrderBy`). Це аналог SQL-запиту `JOIN ... GROUP BY ... ORDER BY`.

**3. Які фактори можуть найбільше впливати на продуктивність складних LINQ-запитів?**
Розмір даних; порядок операцій (фільтрувати й агрегувати якомога раніше); кількість проходів по колекції та повторні обчислення через відкладене виконання; вкладені групування й корельовані підзапити; створення проміжних колекцій і алокації; JIT та прогрів; для баз даних ще й те, чи перекладається запит у SQL.

**4. Як перевірити, що LINQ-пайплайн не лише працює, а й залишається читабельним і підтримуваним?**
Розбити його на методи з промовистими назвами (як `TopProductsByCategory()`), давати проміжним проєкціям зрозумілі імена, коментувати мету й оператори, перевіряти результат тестами або ручним підрахунком (як у нашому розділі перевірки), стежити, щоб один запит не ставав надто довгим, і за потреби виносити частини в окремі кроки. Код-рев'ю й вимірювання часу показують, чи не став пайплайн надто складним.
