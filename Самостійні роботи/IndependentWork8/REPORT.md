# Самостійна робота №8. `Dictionary<TKey, TValue>` та `HashSet<T>` у бібліотеках .NET

Проєкт: `IndependentWork8` (три сценарії: `FileMetadataCache`, `TagManager`, `SearchIndex`). Запуск: `dotnet run`.

## Частина 1. Аналіз використання у відкритих проєктах

Я проаналізував вихідний код двох популярних бібліотек: **Dapper** (micro-ORM, <https://github.com/DapperLib/Dapper>) і **Newtonsoft.Json** (<https://github.com/JamesNK/Newtonsoft.Json>). Нижче посилання на конкретні файли й рядки. Номери рядків наведено для гілки `main`/`master` станом на 22.10.2026: якщо код змінився, шукайте за назвою методу.

### Приклад 1 (Dictionary): таблиця відповідності типів `Type → TypeMapEntry` у Dapper

- **Файл:** [`Dapper/SqlMapper.cs`](https://github.com/DapperLib/Dapper/blob/main/Dapper/SqlMapper.cs#L171) — поле `typeMap` (рядок 171), методи `AddTypeMap` (рядки 284-310), `SetTypeMap` (312), `RemoveTypeMap` (327-337).
- **Контекст:** Dapper має знати, якому `DbType` відповідає кожен .NET-тип параметра (`int`, `string`, `DateTime` тощо). Це робиться для кожного параметра кожного запиту.
- **Чому `Dictionary`:** потрібен пошук за ключем (`Type`) на «гарячому шляху». `List` пошуком перебирав би десятки записів, а `Dictionary` знаходить запис за O(1) у середньому.
- **Складність:** читання O(1); зміна таблиці це клонування за O(n), але вона відбувається вкрай рідко (під час налаштування).
- **Особливість:** автори замість `lock` застосовують підхід «клонувати, змінити, замінити», щоб читачі в різних потоках ніколи не бачили напівзмінену таблицю:

```csharp
// use clone, mutate, replace to avoid threading issues
var snapshot = typeMap;
...
var newCopy = new Dictionary<Type, TypeMapEntry>(snapshot);
newCopy.Remove(type);
SetTypeMap(newCopy);
```

  Ключ `Type` використовує стандартне порівняння (за посиланням), тож власний comparer не потрібен.

### Приклад 2 (HashSet): усунення дублікатів «літеральних токенів» у SQL

- **Файл:** [`Dapper/SqlMapper.cs`](https://github.com/DapperLib/Dapper/blob/main/Dapper/SqlMapper.cs#L2527), метод `GetLiteralTokens` (рядки 2527-2541).
- **Контекст:** у SQL-тексті можуть траплятися позначки вигляду `{=name}`. Метод збирає їх у список, причому кожен токен має потрапити туди **один раз**, навіть якщо зустрічається в запиті кілька разів.
- **Чому `HashSet`:** потрібна лише відповідь «чи бачили ми це слово раніше?». Метод `HashSet<T>.Add` повертає `bool` і одним викликом за O(1) і перевіряє, і додає. З `List` кожна перевірка `Contains` коштувала б O(n), а весь прохід O(n²).

```csharp
var found = new HashSet<string>(StringComparer.Ordinal);
var list = new List<LiteralToken>(matches.Count);
foreach (Match match in matches)
{
    string token = match.Value;
    if (found.Add(match.Value))
    {
        list.Add(new LiteralToken(token, match.Groups[1].Value));
    }
}
```

- **Особливості:** використано власний comparer `StringComparer.Ordinal` (точне порівняння без урахування культури й регістру: швидко і передбачувано). Порядок токенів зберігається окремим `List`, бо `HashSet` порядок не гарантує. Тож тут поєднано дві колекції, кожна для своєї задачі.

### Приклад 3 (Dictionary + HashSet разом): передача параметрів за позицією в Dapper

- **Файл:** [`Dapper/SqlMapper.cs`](https://github.com/DapperLib/Dapper/blob/main/Dapper/SqlMapper.cs#L1907), метод `PassByPosition` (рядки 1907-1950).
- **Контекст:** деякі бази даних приймають параметри лише за позицією (`?`), а користувач передає їх за іменем. Метод замінює імена в тексті запиту на `?` і переставляє параметри.
- **Роль колекцій:**
  - `Dictionary<string, IDbDataParameter> parameters` — «ім'я → параметр»: швидко знайти параметр за іменем з тексту запиту;
  - `HashSet<string> consumed` — «імена, які вже використані»: заборонити використовувати один параметр двічі.

```csharp
Dictionary<string, IDbDataParameter> parameters = new(StringComparer.Ordinal);
...
var consumed = new HashSet<string>(StringComparer.Ordinal);
...
if (!consumed.Add(key))
{
    throw new InvalidOperationException("When passing parameters by position, each parameter can only be referenced once");
}
else if (parameters.TryGetValue(key, out IDbDataParameter? param)) { ... }
```

- **Складність:** кожен збіг у запиті обробляється за O(1) (`Add` + `TryGetValue`), тож весь метод O(m), де m кількість збігів.
- **Comparer:** обидві колекції створені з `StringComparer.Ordinal`, тобто імена параметрів порівнюються однаково в обох структурах (узгодженість comparer-ів важлива).
- Саме цю ж комбінацію (`Dictionary` + `HashSet`) ми використали у власному `SearchIndex`.

### Додатковий приклад (Dictionary): `ThreadSafeStore` у Newtonsoft.Json

- **Файл:** [`Src/Newtonsoft.Json/Utilities/ThreadSafeStore.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/master/Src/Newtonsoft.Json/Utilities/ThreadSafeStore.cs#L39), клас `ThreadSafeStore<TKey, TValue>` (рядок 39).
- **Контекст:** кеш відображень типів (наприклад, контрактів серіалізації): значення дорого створювати, тому їх обчислюють один раз.
- **Чому `Dictionary`:** кеш це класична задача «ключ → значення». У сучасних збірках використовується `ConcurrentDictionary` (потокобезпечний різновид), а у запасному варіанті звичайний `Dictionary` з блокуванням і «подвійною перевіркою» (рядки 76-95): нова копія словника створюється при додаванні, щоб читачі не потребували блокування.

## Частина 2. Практична реалізація

Реалізовано всі три сценарії (код у проєкті):

1. `FileMetadataCache` - `Dictionary<string, FileMetadata>` з `StringComparer.OrdinalIgnoreCase`; `Add` (через `TryAdd`), `Get` (через `TryGetValue`), `Remove`, `Contains`.
2. `TagManager` - `Dictionary<string, HashSet<string>>` (стаття → теги); `AddTag`, `RemoveTag`, `GetAllUniqueTags` (`UnionWith`), `FindCommonTags` (`IntersectWith`), додатково `FindTagsOnlyInFirst` (`ExceptWith`). Теги нечутливі до регістру, тому `C#` і `c#` вважаються одним тегом.
3. `SearchIndex` - `Dictionary<string, HashSet<int>>` (слово → документи); `AddDocument`, `Search`, `SearchMultiple` (перетин `IntersectWith` з раннім виходом, коли результат уже порожній).

Методи, що повертають множини, віддають **копії**, щоб зовнішній код не міг зіпсувати внутрішній стан.

## Частина 3. Порівняльна таблиця

| Операція | `List<T>` | `Dictionary<TKey,TValue>` | `HashSet<T>` | Коли використовувати |
|---|---|---|---|---|
| Додавання | O(1) амортизовано (в кінець); O(n) на початок/середину | O(1) в середньому (O(n) у момент розширення таблиці) | O(1) в середньому | всі три швидкі; `List` для впорядкованих даних, інші два для швидкого доступу |
| Пошук за значенням | O(n) (`Contains`, `IndexOf`) | O(n) (`ContainsValue`), тобто не основна операція | O(1) в середньому (`Contains`) | `HashSet`, коли треба часто питати «чи є такий елемент?» |
| Пошук за ключем | N/A (лише за індексом O(1)) | O(1) в середньому (`TryGetValue`, індексатор) | N/A | `Dictionary`, коли дані мають природний ключ (ID, ім'я файлу, слово) |
| Видалення | O(n) (пошук + зсув елементів) | O(1) в середньому (`Remove(key)`) | O(1) в середньому (`Remove`) | `List` погано підходить для частих видалень із середини |
| Перевірка наявності | O(n) | O(1) (`ContainsKey`) | O(1) (`Contains`) | `Dictionary`/`HashSet` |
| Дублікати | дозволені | ключі унікальні, значення можуть повторюватись | елементи унікальні | `HashSet`, коли дублікати небажані |
| Порядок елементів | зберігається (за індексом) | не гарантується | не гарантується | `List`, якщо порядок важливий |
| Операції над множинами | немає | немає | `UnionWith`, `IntersectWith`, `ExceptWith`, `IsSubsetOf` та ін. | `HashSet` для об'єднання, перетину, різниці |

Складність для хеш-колекцій указана для **середнього випадку**; в гіршому випадку (багато колізій хеш-кодів) операції деградують до O(n). Саме тому важлива якісна реалізація `GetHashCode()` (див. висновки).

## Частина 4. Звіт

### Результати аналізу

В обох бібліотеках словники використовуються там, де потрібен швидкий пошук за ключем у частих операціях (мапінг типів, кеш), а `HashSet` там, де потрібна відповідь «бачили чи ні» й унікальність (усунення дублікатів, облік використаних імен). Автори свідомо вказують comparer (`StringComparer.Ordinal`) і дбають про потокобезпечність (копіювання словника замість блокувань на читання).

### Висновки про вибір колекції

**Коли `Dictionary` краще за `List`?** Коли дані шукають за ключем (ID, ім'я, слово), а не за позицією, і колекція велика. Пошук у `List` це O(n), у `Dictionary` O(1) в середньому. `List` кращий, коли важливі порядок і доступ за індексом або елементів мало.

**Коли `HashSet` оптимальний?** Коли треба перевіряти приналежність (`Contains`), гарантувати унікальність (`Add` повертає `false` для дубліката) або виконувати операції над множинами (об'єднання, перетин, різниця). Не підходить, коли важливий порядок або потрібні дублікати.

**Підводні камені:**
- **Погані `Equals`/`GetHashCode` у власних типах.** Якщо два «однакові» об'єкти мають різні хеш-коди, колекція вважатиме їх різними; якщо хеш-коди збігаються надто часто, операції деградують до O(n). Приклад із методички: `PersonNameComparer` порівнює лише за іменем, тому `John (25)` і `John (30)` вважаються одним елементом.
- **Змінні ключі.** Якщо змінити поле, від якого залежить хеш-код, після додавання в колекцію, елемент «загубиться».
- **Різні comparer-и в пов'язаних колекціях** призводять до неузгодженості (у Dapper обидві структури створені з `Ordinal`).
- **Порядок елементів не гарантується.** Для стабільного виводу треба сортувати (у демонстрації використано `Order()`).
- **Не потокобезпечні.** Для багатьох потоків потрібні `ConcurrentDictionary`, блокування або копіювання (як у Dapper).
- **Не можна змінювати колекцію під час `foreach`** (`InvalidOperationException`).
- **Повернення внутрішньої множини назовні** дозволяє зовнішньому коду зіпсувати стан. Тому наші методи повертають копії.
- **Пам'ять:** хеш-колекції займають більше пам'яті, ніж `List`, і розширюються (rehash) у міру росту.

## Відповіді на контрольні запитання

**1. Які переваги generic-колекцій над неузагальненими структурами даних у .NET?**
Безпека типів (помилки на етапі компіляції, а не `InvalidCastException`), відсутність приведень типів, відсутність упаковки/розпаковки значущих типів (boxing) і тому краща продуктивність, зрозуміліший код (з оголошення видно, що зберігається). Неузагальнені `Hashtable` і `ArrayList` працюють з `object`.

**2. У яких сценаріях доцільніше використовувати `Dictionary<TKey, TValue>`, а в яких `HashSet<T>`?**
`Dictionary` потрібен, коли кожному ключу відповідає **значення**, яке треба швидко знайти (кеш метаданих, мапінг типів, ім'я → параметр). `HashSet` потрібен, коли значення нема, а важлива сама **наявність** елемента та унікальність (унікальні теги, облік вже оброблених елементів, операції над множинами). У пошуковому індексі використовуються обидві структури разом.

**3. Як `IEqualityComparer<T>` впливає на коректність і продуктивність `Dictionary` та `HashSet`?**
Comparer визначає, що вважати «однаковими» ключами й як обчислювати хеш. Коректність: `OrdinalIgnoreCase` робить `"Hello"` і `"HELLO"` одним ключем; неправильний comparer призведе до дублікатів або втрати елементів. Продуктивність: добрий розподіл хеш-кодів дає O(1), велика кількість колізій деградує до O(n); `StringComparer.Ordinal` швидший за порівняння з урахуванням культури. Comparer має бути узгоджений: однакові за `Equals` об'єкти зобов'язані мати однаковий хеш-код.

**4. Чому інвертований індекс зручно будувати саме на базі `Dictionary<string, HashSet<int>>`?**
`Dictionary` за O(1) знаходить слово, а `HashSet<int>` зберігає документи, де воно зустрічається, без дублікатів (слово може повторюватися в документі багато разів, але запис один). Множини дозволяють виконувати багатослівний пошук прямо вбудованими операціями: перетин (`IntersectWith`) для «усі слова» й об'єднання (`UnionWith`) для «будь-яке слово».
