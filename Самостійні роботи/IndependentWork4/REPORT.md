# Самостійна робота №4. Розширення ієрархії та наслідки змін базового класу

Проєкт: `IndependentWork4`. Ієрархія: `LibraryItem` → `Book` → `AudioBook` і `LibraryItem` → `Journal`.
Запуск: `dotnet run`.

## 1. Початкова ієрархія

Спочатку були реалізовані `LibraryItem(title, publicationYear)`, `Book(title, publicationYear, author)` та `Journal(title, publicationYear, issueNumber)`. Кожен похідний клас викликав `base(...)` і перевизначав `DisplayDetails()`. Ця версія скомпілювалася і вивела:

```
Кобзар (1840)
  Автор: Тарас Шевченко
Дзвін (2023)
  Випуск №: 5
```

## 2. Зміна базового класу (крок 4)

У `LibraryItem` додано приватне поле `_uniqueId`, властивість `UniqueId` тільки для читання, а конструктор тепер має вигляд `LibraryItem(string title, int publicationYear, string uniqueId)`.

### Що зламалося

Я змінив **лише** `LibraryItem` і одразу запустив збірку. Компілятор видав дві помилки (по одній на кожен похідний клас, який викликає `base(...)`):

```
Book.cs(10,11):    error CS7036: There is no argument given that corresponds to the
                   required parameter 'uniqueId' of 'LibraryItem.LibraryItem(string, int, string)'
Journal.cs(10,11): error CS7036: There is no argument given that corresponds to the
                   required parameter 'uniqueId' of 'LibraryItem.LibraryItem(string, int, string)'
```

### Які рядки довелося поправити

| Файл | Було | Стало |
|---|---|---|
| `Book.cs` | `public Book(string title, int publicationYear, string author)`<br>`: base(title, publicationYear)` | `public Book(string title, int publicationYear, string author, string uniqueId)`<br>`: base(title, publicationYear, uniqueId)` |
| `Journal.cs` | `public Journal(string title, int publicationYear, int issueNumber)`<br>`: base(title, publicationYear)` | `public Journal(string title, int publicationYear, int issueNumber, string uniqueId)`<br>`: base(title, publicationYear, uniqueId)` |
| `Program.cs` | `new Book("Кобзар", 1840, "Тарас Шевченко")` | `new Book("Кобзар", 1840, "Тарас Шевченко", "BK-001")` (аналогічно для `Journal`) |

Метод `DisplayDetails()` у `Book` і `Journal` змінювати не довелося: він викликає `base.DisplayDetails()`, а та вже сама виводить `UniqueId`. Саме тому в `LibraryItem.DisplayDetails()` рядок з'явився один раз, а ефект видно в усіх нащадках.

### Чому це сталося

У C# конструктор базового класу не успадковується, а кожен похідний конструктор **зобов'язаний** явно (через `base(...)`) або неявно викликати якийсь конструктор базового класу. Коли єдиний конструктор `LibraryItem` отримав третій обов'язковий параметр, неявний виклик `base(title, publicationYear)` перестав відповідати жодній сигнатурі. Похідні класи не знають, звідки взяти `uniqueId`, тому їхні власні конструктори теж довелося розширити, щоб значення можна було прокинути вгору. Це наслідок **жорсткого зв'язування** (tight coupling) між базовим і похідним класом: зміна контракту базового класу ламає всіх нащадків.

Для `AudioBook` ситуація аналогічна, але вже на два рівні: `AudioBook` викликає `Book(...)`, а той викликає `LibraryItem(...)`. Тому `uniqueId` проходить через усі три конструктори.

### Як можна було зменшити шкоду

- Додати **перевантажений** конструктор без `uniqueId`, який генерує його сам (`Guid.NewGuid().ToString()`), а новий залишити поруч: старий код продовжив би компілюватися.
- Зробити `uniqueId` необов'язковим параметром із значенням за замовчуванням.
- Винести створення ідентифікатора в окремий сервіс (див. композицію нижче).

## 3. Розширення ієрархії: AudioBook

`AudioBook : Book` додає поле `_narrator`, властивість `Narrator`, конструктор `AudioBook(title, year, author, narrator, uniqueId)` з викликом `base(...)` і перевизначення `DisplayDetails()`, яке спершу викликає `base.DisplayDetails()` (тобто версію з `Book`, яка вже виводить автора), а потім додає оповідача.

Додавання нового похідного класу **не вимагало жодних змін в існуючих класах**. Це і є розширення без модифікації.

## 4. Розширення vs модифікація (принцип відкритості/закритості, OCP)

| | Новий похідний клас (`AudioBook`) | Зміна базового класу (`UniqueId`) |
|---|---|---|
| Чи чіпаємо існуючий код? | Ні | Так, потенційно всіх нащадків |
| Ризик поломки | Низький: нова поведінка ізольована | Високий: змінюється спільний контракт |
| Чи компілятор допомагає? | Не потрібно | Так, показує всі зламані місця (CS7036) |
| Відповідність OCP | Дотримується («відкритий для розширення») | Порушується («закритий для модифікації») |

## 5. Переваги і недоліки наслідування

**Переваги**
- Спільний код живе в одному місці (`Title`, `PublicationYear`, `UniqueId`, базовий вивід).
- Поліморфізм: `List<LibraryItem>` містить книги, журнали й аудіокниги, і один цикл викликає потрібну версію `DisplayDetails()` для кожного.
- Нову різновидність додати легко (`AudioBook` за 20 рядків).

**Недоліки**
- Жорстке зв'язування: зміна базового класу зачіпає всіх нащадків (ми це побачили на `UniqueId`).
- Глибокі ієрархії важко читати: щоб зрозуміти `AudioBook`, треба знати `Book` і `LibraryItem`.
- Нащадок успадковує **все**, навіть те, що йому не підходить (наприклад, якби `Journal` успадкував `Author`).
- Складно змінити поведінку під час виконання: тип об'єкта фіксується при створенні.

**Коли доцільне:** є справжнє відношення «є різновидом» (is-a), нащадки взаємозамінні за контрактом базового класу (принцип підстановки Лісков), ієрархія неглибока й стабільна.
**Коли призводить до проблем:** наслідування використовують лише заради повторного використання коду, ієрархія глибока, базовий клас часто змінюється, а нащадків багато.

## 6. Композиція замість наслідування

Для цієї задачі композиція могла б бути кращою, наприклад, якщо з'являться різні **способи відображення** або **способи видачі** елементів: замість класів `AudioBookWithRating`, `BookWithDiscount`... можна мати `LibraryItem`, що **містить** об'єкти-стратегії (`IFormatter`, `IIdentifierGenerator`). Тоді зміна в генерації `UniqueId` торкається одного сервісу, а не конструкторів усієї ієрархії. Композиція також дозволяє комбінувати поведінки: наприклад, «аудіокнига, яка також має електронну версію», без множинного наслідування, якого в C# немає.

## Відповіді на контрольні запитання

**1. Як зміна конструктора базового класу вплинула на похідні класи?**
Похідні класи `Book` та `Journal` перестали компілюватися (помилка CS7036), бо їхні виклики `base(title, publicationYear)` більше не відповідали сигнатурі конструктора `LibraryItem`. Довелося додати параметр `uniqueId` у їхні власні конструктори та передати його в `base(...)`, а також оновити створення об'єктів у `Main`. Для `AudioBook` параметр проходить ланцюжком `AudioBook → Book → LibraryItem`.

**2. Чим відрізняється розширення ієрархії через новий похідний клас від модифікації наявного базового класу?**
Новий похідний клас додає поведінку, не торкаючись наявного коду (принцип OCP): існуючі класи й клієнтський код працюють як раніше. Модифікація базового класу змінює спільний контракт, тому впливає на всіх нащадків і всі місця створення об'єктів, і про це доводиться дізнаватися з помилок компіляції або, гірше, з помилок у виконанні.

**3. У яких випадках для цієї задачі композиція могла б бути кращою за наслідування?**
Коли різновидів стає багато і вони комбінуються (аудіо + електронна версія + позначка «нове надходження»), коли поведінку треба змінювати під час виконання або коли частина логіки (генерація ідентифікатора, форматування виводу) не належить логічно до «бути різновидом елемента». Тоді її виносять в окремі об'єкти й підставляють у `LibraryItem` через інтерфейс.

**4. Як поліморфний виклик `DisplayDetails()` допомагає перевірити правильність ієрархії?**
Цикл `foreach (LibraryItem item in catalog) item.DisplayDetails();` працює з усіма типами однаково. Якщо якийсь клас неправильно перевизначив метод (забув `base.DisplayDetails()` чи не став `override`), це одразу видно у виводі: у рядку немає ID або автора. Так само перевіряється принцип підстановки: будь-який нащадок має коректно працювати там, де очікується `LibraryItem`.
