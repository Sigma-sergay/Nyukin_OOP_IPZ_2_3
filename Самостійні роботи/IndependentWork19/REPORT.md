## 1. Власний тип винятку `InsufficientStockException`

```csharp
public class InsufficientStockException : Exception
{
    public string? Sku { get; }
    public int RequestedQuantity { get; }
    public int AvailableQuantity { get; }

    public InsufficientStockException() { }
    public InsufficientStockException(string message) : base(message) { }
    public InsufficientStockException(string message, Exception innerException) : base(message, innerException) { }

    public InsufficientStockException(string sku, int requested, int available)
        : base($"Недостатньо товару {sku}: запитано {requested}, доступно {available}.") { … }
}
```

- Назва закінчується на `Exception`, клас успадковує `System.Exception`.
- Реалізовано **три стандартні конструктори** (без параметрів, з `message`, з `message` + `innerException`) і один доменний.
- Додаткові властивості (`Sku`, `RequestedQuantity`, `AvailableQuantity`) дають обробнику контекст: можна показати користувачу «доступно лише 3 шт.», не розбираючи текст повідомлення.
- У `Main` показано три речі: перехоплення через `try-catch-finally`, обгортання низькорівневого `KeyNotFoundException` через `innerException` разом із фільтром `catch … when`, і альтернативу через `Result<T>`.

Вивід:

```
Перехоплено InsufficientStockException: Недостатньо товару SKU-KB-01: запитано 10, доступно 3.
  Sku=SKU-KB-01, RequestedQuantity=10, AvailableQuantity=3
finally: блок завершено (тут звільняли б ресурси, наприклад транзакцію)
Перехоплено з InnerException: Товар SKU-MS-02 відсутній у старій складській системі. ← KeyNotFoundException
Result.Failure: товару SKU-MS-02 немає в наявності (доступно 0)
```

## 2. Сценарії Polly

### Сценарій A — Retry: API курсів валют

**Проблема.** Під час оформлення замовлення в доларах магазин запитує курс у банківського API. API іноді відповідає `503` через перевантаження, але за частку секунди відновлюється. Падати через це оформлення не повинно.

**Стратегія:** `Retry` з експоненційною затримкою та jitter. Збій короткочасний і безпечний для повтору: читання курсу ідемпотентне. Jitter потрібен, бо багато покупців звертаються до того самого API одночасно.

```csharp
new ResiliencePipelineBuilder<decimal>()
    .AddRetry(new RetryStrategyOptions<decimal>
    {
        ShouldHandle = new PredicateBuilder<decimal>().Handle<HttpRequestException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(200),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args => { Log($"Retry #{args.AttemptNumber + 1} через {args.RetryDelay.TotalMilliseconds:F0} мс …"); return default; }
    })
    .Build();
```

**Вивід:**

```
Retry #1 через 205 мс (причина: 503 від api.bank.example: сервіс перевантажений)
Retry #2 через 151 мс (причина: 503 від api.bank.example: сервіс перевантажений)
Курс USD отримано: 41,37 грн (викликів API: 3)
```

Дві невдачі, третя спроба успішна. Затримки не строго 200 → 400, бо Polly використовує jitter (decorrelated jitter), який навмисно робить паузи випадковими.

### Сценарій B — Circuit Breaker: платіжний шлюз (не Retry)

**Проблема.** Платіжний провайдер повністю «ліг» (`502 Bad Gateway`). Якщо кожне замовлення продовжить звертатися до нього (та ще й з retry), користувачі чекатимуть таймаутів, а провайдер під час відновлення отримає лавину запитів.

**Стратегія:** `Circuit Breaker`. Після того як за 10 с серед щонайменше 3 викликів набереться ≥50 % невдач, ланцюг **розмикається** на 1 с. Поки він розімкнений, виклики відхиляються одразу (`BrokenCircuitException`), і магазин пропонує «оплатити пізніше». Після паузи ланцюг переходить у напіввідкритий стан і пропускає один пробний виклик: якщо той успішний, ланцюг замикається.

```csharp
.AddCircuitBreaker(new CircuitBreakerStrategyOptions<string>
{
    ShouldHandle = new PredicateBuilder<string>().Handle<HttpRequestException>(),
    FailureRatio = 0.5,
    MinimumThroughput = 3,
    SamplingDuration = TimeSpan.FromSeconds(10),
    BreakDuration = TimeSpan.FromSeconds(1),
    OnOpened = …, OnHalfOpened = …, OnClosed = …
})
```

**Вивід:**

```
Замовлення #1: помилка шлюзу — 502 Bad Gateway від платіжного провайдера
Замовлення #2: помилка шлюзу — 502 Bad Gateway від платіжного провайдера
⚡ Ланцюг РОЗІМКНЕНО на 1 c
Замовлення #3: помилка шлюзу — 502 Bad Gateway від платіжного провайдера
Замовлення #4: шлюз НЕ викликався (fail-fast), запропонувати оплату пізніше
Замовлення #5: шлюз НЕ викликався (fail-fast), запропонувати оплату пізніше
…чекаємо 1.2 c, поки мине BreakDuration…
◐ Ланцюг напіввідкритий: пробний виклик
● Ланцюг ЗАМКНЕНО: шлюз знову працює
Замовлення #6: оплачено, чек PAY-0006-499
Замовлення #7: оплачено, чек PAY-0007-499
Реальних викликів шлюзу: 5 з 7 замовлень
```

Замовлення #4 і #5 не навантажили провайдера й відразу отримали відповідь. Retry тут лише погіршив би ситуацію, тому для платежів обрано саме Circuit Breaker. До того ж оплата **неідемпотентна**, і повторювати її наосліп небезпечно.

### Сценарій C — Timeout + Fallback: каталог товарів

**Проблема.** Запит до бази даних каталогу іноді «зависає» на кілька секунд (блокування, повільний план запиту). Головна сторінка магазину не повинна чекати 3 с.

**Стратегія:** комбінація `Timeout` (500 мс) і `Fallback`. Timeout скасовує запит через `CancellationToken`, а Fallback перехоплює `TimeoutRejectedException` і повертає кешовану версію каталогу. Користувач бачить трохи застарілі дані замість помилки. Порядок у pipeline важливий: Fallback зовнішній, Timeout внутрішній.

```csharp
new ResiliencePipelineBuilder<List<string>>()
    .AddFallback(new FallbackStrategyOptions<List<string>>
    {
        ShouldHandle = new PredicateBuilder<List<string>>().Handle<TimeoutRejectedException>(),
        FallbackAction = _ => Outcome.FromResultAsValueTask(cachedCatalog),
    })
    .AddTimeout(new TimeoutStrategyOptions { Timeout = TimeSpan.FromMilliseconds(500) })
    .Build();
```

**Вивід:**

```
Швидкий запит: Клавіатура, Мишка, Монітор, Навушники
⏱ Запит перевищив 500 мс — скасовано
↩ Fallback: повертаємо каталог із кешу
Повільний запит: Клавіатура (кеш), Мишка (кеш), Монітор (кеш)
```

## 3. Коли кидати виняток, а коли повертати `Result<T>`

Виняток слід кидати у **виняткових** ситуаціях, які порушують контракт методу або нормальний стан системи: зник файл конфігурації, розірвалося з'єднання з БД, прийшов `null` там, де він неприпустимий, або всередині складу виявилась внутрішня невідповідність. Такі помилки неможливо проігнорувати, вони несуть стек викликів і мають «спливти» до місця, яке знає, що робити. `Result<T>` (або `bool TryXxx(out …)`, або `null`) доречний для **очікуваних** неуспіхів, які є частиною бізнес-логіки: товару немає в наявності, користувач ввів неправильний промокод, пошук нічого не знайшов. Вони трапляються часто, їх обробка — звичайна гілка коду, і розкручування стека тут лише сповільнює програму та ховає логіку в `catch`. У роботі це видно на складі: `Reserve` кидає `InsufficientStockException` (виклик, який не очікує нестачі), а `TryReserve` повертає `Result<int>.Failure` для перевірки наявності в кошику.

## 4. Висновки щодо переваг і обмежень Polly

**Переваги:**

- Логіка відмовостійкості відокремлена від бізнес-коду. Pipeline налаштовується декларативно й повторно використовується.
- Готові перевірені стратегії (Retry з jitter, Circuit Breaker, Timeout, Fallback, Rate Limiter, Hedging), які легко комбінуються в pipeline.
- Колбеки `OnRetry`, `OnOpened`, `OnTimeout` дають зручне логування й телеметрію.
- `PredicateBuilder` дозволяє точно вказати, які винятки чи результати вважати збоєм.

**Обмеження:**

- Polly не робить операцію безпечною для повтору: про ідемпотентність має подбати розробник.
- Неправильні параметри (завеликий `MaxRetryAttempts`, короткий `BreakDuration`) можуть посилити навантаження під час аварії.
- Порядок стратегій у pipeline впливає на поведінку, і помилку в ньому легко не помітити.
- Це додаткова залежність і додаткова складність. Для простого локального коду власний невеликий retry (як у самостійній №20) може бути достатнім.
- Circuit Breaker зберігає стан, тому pipeline треба використовувати повторно (singleton), а не створювати на кожен виклик.

## 5. Відповіді на контрольні запитання

**1. Різниця між «кидати виняток» і «повертати Result».** Виняток перериває нормальний потік і передається вгору стеком, доки його не перехоплять. Він підходить для непередбачених ситуацій: `throw new InsufficientStockException(sku, 10, 3)`, коли резервування викликали без перевірки. `Result` — звичайне значення, яке викликач перевіряє `if`-ом. Він підходить для очікуваних неуспіхів: `var r = warehouse.TryReserve(sku, 1); if (!r.IsSuccess) ShowMessage(r.Error);`.

**2. Три стандартні конструктори власного винятку:** `()`, `(string message)`, `(string message, Exception innerException)`. Вони потрібні, щоб виняток можна було створити в будь-якому стандартному сценарії, зокрема обгорнути низькорівневу помилку, не втративши її (`InnerException`).

**3. Circuit Breaker vs Retry.** Retry **повторює** невдалий виклик, сподіваючись, що збій короткий. Circuit Breaker **припиняє** виклики, коли збоїв забагато, і швидко повертає помилку, даючи сервісу відновитися. Retry доцільний для поодиноких тимчасових збоїв (сценарій A). Circuit Breaker доцільний, коли залежність недоступна тривало (сценарій B). Часто їх комбінують: Retry зовні, Circuit Breaker всередині.

**4. Bulkhead.** Bulkhead («перегородка») обмежує кількість одночасних викликів певної залежності (у Polly v8 це `AddConcurrencyLimiter` / Rate Limiter). Він вирішує проблему, коли одна повільна залежність займає всі потоки чи з'єднання застосунку, і через неї перестають працювати навіть незалежні функції. Аналогія — водонепроникні відсіки корабля.

**5. Навіщо jitter.** Без jitter усі клієнти, що отримали помилку одночасно, повторюють запит теж одночасно (через 200, 400, 800 мс). Так виникають хвилі навантаження (thundering herd), які знову валять сервіс. Випадкове відхилення розмазує повтори в часі.

**6. Ризики Retry для неідемпотентної операції.** Якщо запит фактично виконався, а відповідь загубилась (таймаут), повтор виконає дію **ще раз**: подвійне списання коштів, два однакові замовлення, два листи. Такі операції або не повторюють, або роблять ідемпотентними через ключ ідемпотентності чи перевірку стану перед повтором.
