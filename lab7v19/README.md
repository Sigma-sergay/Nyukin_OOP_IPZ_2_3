# Лабораторна робота №7 — Generics, IRepository<T> з where-обмеженнями та тестами (варіант 19)

## Опис

- **`IEntity`** — інтерфейс з єдиною властивістю `int Id { get; set; }`. Усі сутності, що зберігаються в репозиторії, мають його реалізувати.
- **`Notification`** (сутність варіанту 19) — `Id`, `Message` (string), `RecipientId` (int), `IsRead` (bool). Реалізує `IEntity`.
- **`IRepository<T> where T : IEntity`** — методи `T? GetById(int id)`, `IEnumerable<T> GetAll()`, `void Add(T item)`, `void Update(T item)`, `void Delete(int id)`.
- **`InMemoryRepository<T> where T : IEntity`** — зберігає елементи у `List<T>`.

### Поведінка в особливих випадках

| Операція | Нормальний випадок | Особливий випадок |
|---|---|---|
| `Add` | додає елемент; якщо `Id == 0`, призначає унікальний `Id` | дублікат `Id` → `ArgumentException`; `null` → `ArgumentNullException` |
| `GetById` | повертає елемент | неіснуючий `Id` → `null` |
| `GetAll` | повертає **копію** списку | порожній репозиторій → порожня колекція |
| `Update` | замінює елемент з тим самим `Id` | неіснуючий → `KeyNotFoundException`; `null` → `ArgumentNullException` |
| `Delete` | видаляє елемент, інші лишаються | неіснуючий `Id` → `KeyNotFoundException` |

### Тести (16 штук)

Для кожного методу є тест нормальної поведінки та тест на неіснуючий елемент або некоректні дані: `Add` (5), `GetById` (2), `GetAll` (3), `Update` (3), `Delete` (3).

## Відповіді на контрольні запитання

### 1. Роль `where`-обмежень у Generics. Приклади

Без обмежень компілятор про тип `T` знає лише те, що це «якийсь `object`», тому всередині узагальненого коду можна викликати тільки методи `object`. Обмеження `where` розповідають компілятору, що саме гарантовано вміє тип-аргумент, і це дає дві речі: **можливість використовувати ці члени** в узагальненому коді та **перевірку на етапі компіляції**, що хтось не підставить непідходящий тип.

Основні обмеження:

- `where T : class` / `where T : struct` — лише посилальний / лише значущий тип.
- `where T : new()` — тип має публічний конструктор без параметрів, тож можна написати `new T()`.
- `where T : IInterface` або `where T : BaseClass` — тип реалізує інтерфейс або успадковує клас.
- `where T : U` — `T` має бути `U` або його похідним.

Приклад з лабораторної: `IRepository<T> where T : IEntity`. Завдяки цьому в `InMemoryRepository<T>` ми можемо написати `x.Id == id` і `item.Id = _nextId++`, хоча про конкретний тип нічого не знаємо. Спроба створити `InMemoryRepository<string>` не скомпілюється, бо `string` не реалізує `IEntity`.

### 2. Навіщо потрібен шаблон IRepository. Переваги

`IRepository` ховає за інтерфейсом спосіб зберігання даних: бізнес-логіка просто викликає `Add`, `GetById` тощо й не знає, чи це список у пам'яті, база даних чи файл.

Переваги:

- **Заміна сховища без змін у бізнес-логіці**: сьогодні `InMemoryRepository`, завтра репозиторій на Entity Framework, і код, що користується `IRepository<T>`, лишається незмінним.
- **Тестованість**: у тестах можна підставити швидкий репозиторій у пам'яті замість справжньої бази.
- **Єдине місце для доступу до даних**: немає розкиданого по програмі коду запитів, простіше підтримувати.
- **Повторне використання**: один узагальнений репозиторій обслуговує всі сутності (`Notification`, `User`, `Product`).
- **Слабке зв'язування** (loose coupling) і дотримання принципу інверсії залежностей (залежність від абстракції, а не від реалізації).

### 3. Чому юніт-тести важливі для узагальнених компонентів

Узагальнений код пишеться один раз, але використовується з багатьма типами, тому помилка в ньому проявляється всюди одночасно. Тести дозволяють:

- **швидко виявити помилку** в одному місці, а не шукати її в усіх сутностях, що користуються репозиторієм;
- **зафіксувати контракт**: що робить `GetById` для неіснуючого `Id`, що кидає `Update` — це описано виконуваним кодом, а не лише словами;
- **безпечно рефакторити**: якщо змінити реалізацію (наприклад, `List<T>` на `Dictionary<int, T>`), зелені тести підтверджують, що поведінка не змінилась;
- **перевірити граничні випадки** (порожній репозиторій, дублікат `Id`, `null`), про які легко забути при ручній перевірці через `Main`;
- **документувати поведінку** для інших розробників.

Узагальнений компонент у принципі варто перевіряти хоча б на кількох типах-аргументах (наприклад, на значущому й посилальному), бо поведінка `default(T)` у них різна.

### 4. Які проблеми вирішують Generics порівняно з `object`

Колекція або метод на основі `object` приймає що завгодно, і це створює проблеми, які Generics усувають:

1. **Безпека типів.** З `List<object>` можна покласти `int` і `string` разом, а помилка проявиться лише під час виконання (`InvalidCastException`). `List<Notification>` не дозволить додати чужий тип: помилка буде на етапі компіляції.
2. **Не потрібні приведення типів.** З `object` кожне читання вимагає `(Notification)list[0]`; з generics це зайве.
3. **Продуктивність: немає boxing/unboxing.** Якщо в `object` покласти значущий тип (`int`, `double`), він пакується в купу (boxing), що викликає виділення пам'яті та навантаження на збирач сміття. `List<int>` зберігає числа напряму.
4. **Читабельність і підтримка IDE.** Тип видно з оголошення, працює автодоповнення, а компілятор перевіряє код.
5. **Повторне використання без дублювання.** Один `InMemoryRepository<T>` замість окремого класу для кожної сутності й без втрати типізації.
