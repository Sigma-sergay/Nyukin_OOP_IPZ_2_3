## RetryHelper

```csharp
public static T ExecuteWithRetry<T>(
    Func<T> operation,
    int retryCount = 3,
    TimeSpan initialDelay = default,
    Func<Exception, bool>? shouldRetry = null)
```

- `retryCount` — кількість **повторних** спроб, тобто всього спроб `retryCount + 1`;
- перед кожним повтором чекає `initialDelay * 2^(attempt - 1)`;
- кожну спробу та причину невдачі логує в консоль із часовою позначкою;
- якщо `shouldRetry(ex)` повертає `false`, виняток одразу прокидається далі (`throw;` зберігає stack trace);
- якщо спроби вичерпано, прокидається останній виняток.

## Сценарії в `Main`

| № | Сценарій | Результат |
|---|----------|-----------|
| 1 | `ReadDatabaseDump`: 2 × `FileNotFoundException` | успіх з 3-ї спроби, затримки 200 і 400 мс |
| 2 | `QueryDatabase`: 3 × `HttpRequestException` | успіх з 4-ї спроби, затримки 200, 400 і 800 мс |
| 3 | `UnauthorizedAccessException` (немає прав) | `shouldRetry = false`: жодного повтору, виняток перехоплено в `Main` |
| 4 | Мережа недоступна довше, ніж дозволяє `retryCount = 2` | 3 спроби, після чого `HttpRequestException` перехоплено в `Main` |

## Висновок

Затримка між спробами росте експоненційно: `initialDelay * 2^(n-1)`, тобто 200 → 400 → 800 мс. Тому в сценарії 2 запит до сервера БД, який тричі не відповідає, сумарно чекає лише ≈ 1,4 с: короткий збій долається швидко. Якщо ж сервер недоступний довше, паузи зростають, і застосунок не перевантажує його потоком повторних запитів.

## Відповіді на контрольні запитання

### 1. Які типи винятків найчастіше виникають при роботі з файлами та мережею

**Файли (IO):**

- `FileNotFoundException`: файлу не існує;
- `DirectoryNotFoundException`: немає каталогу зі шляху;
- `IOException`: загальна помилка вводу/виводу, наприклад файл зайнятий іншим процесом;
- `UnauthorizedAccessException`: немає прав доступу;
- `PathTooLongException`, `ArgumentException`: некоректний шлях.

**Мережа:**

- `HttpRequestException`: помилка HTTP-запиту (сервер недоступний, DNS, код 5xx через `EnsureSuccessStatusCode`);
- `SocketException`: низькорівнева помилка сокета (з'єднання відхилено чи розірвано);
- `TaskCanceledException` / `TimeoutException`: перевищено час очікування;
- `WebException`: у старому API.

### 2. Принцип роботи патерну Retry. Коли його доцільно використовувати

Retry означає: якщо операція завершилась **тимчасовою** помилкою, її повторюють кілька разів із паузою між спробами. Помилка прокидається далі тільки тоді, коли спроби вичерпано. Патерн доцільний для **транзієнтних** збоїв, які зникають самі:

- короткочасна недоступність мережі чи сервера, таймаут;
- файл тимчасово заблокований іншим процесом або ще не створений;
- перевантаження сервера (HTTP 503, 429).

Retry **не** варто застосовувати до постійних помилок (немає прав, неправильний шлях, синтаксична помилка в запиті, 404), бо повтор нічого не змінить. Також не варто повторювати неідемпотентні операції (наприклад, списання коштів) без додаткового захисту від дублювання.

### 3. Як реалізувати експоненційну затримку між повторними спробами

Після невдалої спроби з номером `n` затримка обчислюється як

```
delay = initialDelay * 2^(n - 1)
```

У коді:

```csharp
var wait = TimeSpan.FromMilliseconds(initialDelay.TotalMilliseconds * Math.Pow(2, attempt - 1));
Thread.Sleep(wait);   // в асинхронному коді — await Task.Delay(wait)
```

Для `initialDelay = 200 мс` це 200, 400, 800, 1600 мс. На практиці часто додають **верхню межу** (max delay) і **jitter**, тобто невелику випадкову добавку, щоб багато клієнтів не повторювали запити одночасно.

### 4. Для чого потрібен делегат `shouldRetry` у `RetryHelper`

`shouldRetry` (`Func<Exception, bool>`) дозволяє **вибірково** вирішувати, які помилки повторювати. `RetryHelper` узагальнений і нічого не знає про конкретну операцію, тому рішення «ця помилка тимчасова чи постійна» передається ззовні:

```csharp
Func<Exception, bool> shouldRetry = ex => ex is FileNotFoundException or HttpRequestException;
```

Завдяки цьому тимчасові помилки (`FileNotFoundException` поки бекап ще пишеться, `HttpRequestException` при збої мережі) повторюються, а постійні (`UnauthorizedAccessException` у сценарії 3) одразу прокидаються в `Main` без зайвих затримок. Один і той самий `RetryHelper` можна використовувати з різними правилами для різних операцій.
